# Internationalisation (i18n) and time

## 1. Decisions

| Decision | Choice | Why |
|---|---|---|
| Source language | English | Contributors and reviewers share it; keys/events already English |
| Catalog format | gettext `.po` per language under `locales/<lang>/LC_MESSAGES/messages.po`, one `messages.pot` | Standard tooling, plurals and contexts |
| Tooling | Babel (extraction, catalogs, locale data for formatting) | Mature CLDR data; permissive licence |
| Shipped languages | `en` (source), `tr` | Owner's users; more can be added by adding a `.po` |
| Missing translation | Falls back to English | Never show a key or empty string |
| Stored data | Language-independent | Language switch must not require reprocessing or migrations |

## 2. Marking strings

| Where | Marker |
|---|---|
| Python, at use | `_("Text {name}", name=value)` — named placeholders only, formatted after translation |
| Plurals | `ngettext("{n} person", "{n} people", n)` — `{n}` provided automatically |
| Context (same English, different meaning) | `pgettext("call state", "Answered")` |
| Module-level constants (labels in manifests, enums) | `N_("Text")` / `NP_(context, "Text")` to mark; translate at display with `_(value)` / `tr_(value)` |
| Jinja2 templates | the i18n extension: `{% trans %}…{% endtrans %}`, `{{ _("…") }}`, `{% trans count=n %}` |
| JavaScript | `T("Text {n}", {n: 5})`; the page embeds only the strings its scripts use (generated list) via the safe JSON helper |

Rules:
- **Never build a sentence from fragments** ("You have " + n + " items"): word order differs per language.
- **Never put an f-string or concatenation inside `_()`**: extractors cannot see dynamic text, and the
  translation lookup would miss. Use named placeholders.
- Do not use `_` as a throw-away variable name anywhere (`for key, _, x in …`): it shadows the translation
  function and fails at runtime in that scope. The check tool flags it.
- Attribute values, tooltips and JSON use the function form (`_()`), which escapes correctly in context;
  autoescape handles HTML.
- Bold/links inside a sentence: use placeholders for the markup-bearing parts and mark the HTML-safe
  result explicitly, or split into translatable units that are complete phrases.
- Domain terms that are easily confused get a context and a glossary entry in the module doc §11
  (e.g. "1:1 call" vs "meeting" vs "group call" must be used consistently everywhere).

## 3. Catalog workflow (tool)

`i18n` tool commands:

| Command | Effect |
|---|---|
| `extract` / `sync` | extract from Python, templates and JS markers → update `.pot`, merge into every `.po`, mark obsolete |
| `add <lang> <map.json>` | apply translations from an English → target JSON map (overwriting existing entries intentionally) |
| `stats` | translated / fuzzy / missing per language |
| `check` | CI gate: fails on missing translations in shipped languages, on bare user-visible strings not wrapped in a marker (heuristic, with an explicit ignore comment), and on `_` shadowing |

Catalogs are compiled to `.mo` at build/deploy time (or loaded from `.po` in development with reload on
change). Fuzzy entries count as missing.

**Pseudo-locale `xx`:** renders every translated string wrapped and accented (`[Ŝéttîñĝš]`). Any plain
English visible in `xx` screenshots is unmarked text. Available only when `APP_DEBUG_LOCALES=on`.

## 4. Language selection (web)

Order per request: cookie `ta_lang` → user's stored `app_users.locale` (copied to the cookie at login) →
`Accept-Language` best match among shipped languages → `APP_LANGUAGE` env → `en`.

- Switch: `GET /lang?l=<code>&next=<relative path>` sets the cookie and `app_users.locale` (no CSRF needed
  — preference only, but `next` must be a same-site relative path).
- `<html lang="…">` always set; JS reads `document.documentElement.lang` for `Intl` and sorting (never a
  hard-coded locale).
- CLI output and log messages are English and not translated (logs are for operators/developers).

## 5. Formatting helpers (the only way to format)

| Helper | Behaviour |
|---|---|
| `fmt_int(n)`, `fmt_num(x, digits)` | locale grouping/decimal separators |
| `fmt_pct(x, digits)` | locale percent pattern (`50%` en, `%50` tr) |
| `fmt_date(d)` | locale medium date (tr `dd.MM.yyyy`; en/unknown → ISO `yyyy-MM-dd` for unambiguity) |
| `fmt_time(t)` | locale 12/24 h |
| `fmt_datetime(dt)` | date + time in the app timezone |
| `fmt_duration(seconds)` | compact `1 h 05 min`, `45 s` (translated units) |
| `weekdays()`, `first_weekday()` | locale names and week start (heatmaps) |
| `tz_city()` | display name of the app timezone (for "times shown in …" notes) |

JS mirrors: `Intl.NumberFormat(lang)`, `Intl.DateTimeFormat(lang, {timeZone})` with the server-provided
timezone and date pattern. Exports (CSV) use ISO dates/times in the app timezone and plain numbers
(dot decimal) for machine readability; column headers in the viewer's language.

## 6. Language-independent stored data

- Derived data and audit details store **codes and parameters**, never sentences: e.g. outcome
  `{code: "unanswered"}`, event `{offset_s, kind, code, p: {...}}`, permission detail `device_api:404`.
- Label helpers (one module per area, e.g. `labels.py` in each module) turn codes into translated text at
  render time: outcome labels, platform names, bot types, event descriptions, permission detail texts,
  audit view descriptions.
- Seeded role names/descriptions and module/package labels are English msgids translated at display;
  user-created role names are shown as typed.
- Internal keys (module, package, feature, setting, scope type, detail level, event key, role key) are
  English identifiers and never translated or renamed for language reasons.
- Search: accent/case folding for name search is language-independent (`search_fold`: Unicode case fold +
  strip combining marks + Turkish dotless/dotted i normalised to `i`); the same function exists in JS.

## 7. Time and timezone

- All stored timestamps are UTC (`timestamptz`). Derived data contains no local times.
- One application timezone: env `APP_TIMEZONE` (IANA name, e.g. `Europe/Istanbul`); fallback setting
  `timezone`; final fallback `UTC`. Python exposes it as one constant; SQL exposes `app_tz()` reading the
  session setting `app.tz` that every connection sets.
- SQL views that bucket by local hour/day/weekday use `app_tz()` — never a literal zone.
- UI states the timezone where hours matter ("Hours in Europe/Istanbul time").
- Changing the timezone needs no reprocess; it changes only presentation and local bucketing.
- Day boundaries for "last N days" ranges are computed in the app timezone, then converted to UTC for
  queries. Range parameters in APIs: `from` inclusive, `to` exclusive.

## 8. Verification

- `check` passes in CI.
- Screenshots of each touched screen in `en`, `tr` and `xx`.
- For refactors that should not change text: render with a fixed "now" before and after and diff
  (render-check tool), in each language.
